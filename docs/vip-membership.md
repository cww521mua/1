# 会员体系设计方案（普通用户 / VIP / SVIP）

> 状态：**设计提案，未实现**。本文档描述在现有卡密 + 多用户体系上叠加三级会员的完整方案，供评审后分期实施。

## 一、背景与目标

当前面板的用户模型是「超级管理员 + 普通用户」二元结构：普通用户由时间卡注册，受统一的账号上限（默认 2 个）约束，功能全量开放。引入会员等级的目标：

1. **售卖分层**：为不同付费能力的人群提供差异化权益，支撑 VIP / SVIP 定价。
2. **功能分层**：高等级解锁更多自动化能力（好友互动、神秘商人抢购等），形成升级动力。
3. **资源公平**：同一实例上多用户共享游戏网关，高等级用户的请求调度优先。
4. **复用现有体系**：会员通过卡密开通与续费，不引入支付、订单等新系统。

## 二、等级与权益建议

| 权益 | 普通用户 | VIP | SVIP |
| --- | --- | --- | --- |
| 账号数量上限 | 2（现状） | 5 | 10 |
| 农场基础自动化（收获/种植/浇水/除草/除虫/出售） | ✅ | ✅ | ✅ |
| 日常任务与免费礼包 | ✅ | ✅ | ✅ |
| 土地升级 | ✅ | ✅ | ✅ |
| 好友互动（访问/帮忙/偷菜/自动接受好友） | ❌ | ✅ | ✅ |
| 自动施肥与化肥购买 | ❌ | ✅ | ✅ |
| 安静时段、好友黑名单等精细化策略 | ✅ | ✅ | ✅ |
| 好友捣乱（放草/放虫） | ❌ | ❌ | ✅ |
| 神秘商人自动抢购（含金币/钻石额度开关） | ❌ | ❌ | ✅ |
| 离线提醒推送（pushoo 渠道） | ❌ | ✅ | ✅ |
| QQ 扫码登录 | ❌ | ✅ | ✅ |
| 请求调度优先级 | 普通 | 优先 | 最高 |
| 图鉴 / 分析 / 活动中心 | ✅ | ✅ | ✅ |

说明：

- 上表数值均为**建议默认值**。权益表在实现上应为一个集中定义的常量（或超管可调的配置），避免散落在代码里。
- 「账号数量上限」取 `max(等级基础上限, 额度卡叠加值)`：等级提供底线，额度卡仍可叠加，两者兼容。
- 好友捣乱与神秘商人抢购是典型的「伤人缘 / 高价值」功能，放在 SVIP 拉开差距。

## 三、核心设计

### 3.1 数据模型

**用户**（`core/data/users.json`）新增两个字段：

```json
{
  "username": "buyer01",
  "level": "vip",
  "levelExpiresAt": 1794992000000,
  "card":   { "expiresAt": 1797584000000 },
  "accountLimit": 5
}
```

| 字段 | 说明 |
| --- | --- |
| `level` | `normal` / `vip` / `svip`，缺省 `normal` |
| `levelExpiresAt` | 等级到期时间；`null` 表示永久。到期后自动降级为 `normal`，等级时长不删除 |
| `card.expiresAt` | 账号有效期（现有字段，不变）：到期则整个账号无法登录 |

两个到期时间相互独立：账号有效期决定「能不能登录」，等级到期决定「享受哪档权益」。

**卡密**（`core/data/cards.json`）新增一个字段：

```json
{ "type": "time", "grantLevel": "vip", "durationValue": 30, "durationUnit": "day", ... }
```

| 字段 | 说明 |
| --- | --- |
| `grantLevel` | 卡密携带的等级属性：`none`（默认，即普通时间卡）/ `vip` / `svip`。额度卡同样可携带 |

卡密管理页生成卡密时增加「赋予等级」选择；列表增加等级徽标。这样「VIP 月卡」「SVIP 季卡」就是 `grantLevel=vip/svip` 的时间卡，**不需要新增卡密类型**。

### 3.2 升级与续费规则（关键状态机）

核销/注册一张卡密时（`grantLevel = L`，卡密时长 = D）：

```
注册（新用户）:
  level          = L（none 则为 normal）
  levelExpiresAt = now + D
  expiresAt      = now + D          ← 与现有注册行为一致

续费（已有用户）:
  expiresAt      = max(expiresAt, now) + D        ← 任何卡都续账号有效期
  若 L 是等级卡:
    levelExpiresAt = max(levelExpiresAt, now) + D
    level = (L >= 当前 level) ? L : 当前 level   ← 高等级用户用低等级卡不掉级
  若 L 是普通卡:
    level 不变（等级到期照常计时）
```

规则要点：

- **不掉级**：SVIP 用户用普通时间卡续费，只延长账号有效期，等级与等级到期不受影响。
- **按时升级不重置**：VIP 用户再买 SVIP 卡 → 直接升 SVIP，等级时长从剩余时间上叠加（与现有 `computeNextExpiresAt` 逻辑一致）。
- **低等级卡给高等级用户**：只续时长、不触发等级变化，避免「买一个月普通卡把 SVIP 冲掉」。
- 额度卡的 `grantLevel` 同理生效（例如「SVIP 专属 +3 额度卡」）。

### 3.3 降级与到期巡检

复用现有的每分钟巡检（`admin/index.ts` 的 `sweepExpiredAccounts`），扩展一个分支：

```
levelExpiresAt 不为空且 < now:
  user.level = 'normal'
  user.levelExpiresAt 清空（或保留原值仅作记录）
  将该用户名下账号配置中超权的 automation 键重置为关闭（见 3.4）
  写入账号日志：「会员等级已到期，已降级为普通用户」
```

降级不删数据、不停账号，只收回超权功能。续费后等级恢复，重新打开开关即可（或降级时不重置、仅靠保存校验拦截，二选一，见 3.4 的取舍）。

### 3.4 功能门控

新增集中权益表（建议 `core/src/config/tier-permissions.ts`）：

```ts
const TIER_PERMISSIONS = {
  normal: { accountLimit: 2, features: ['farm', 'farm_push', 'sell', 'task', 'land_upgrade', 'skip_own_weed_bug', 'show_manual_fertilizer', 'friendQuietHours', 'plantBlacklist'] },
  vip:    { accountLimit: 5, features: [...normal, 'friend', 'friend_auto_accept', 'friend_steal', 'friend_help', 'fertilizer', 'fertilizer_buy_organic', 'fertilizer_buy_normal', 'offlineReminder'] },
  svip:   { accountLimit: 10, features: [...vip, 'friend_bad', 'mystery_shop_auto_buy', 'mystery_shop_allow_*', 'qqQrLogin', 'priorityHigh'] },
};
```

门控点分三层，按实施成本递增：

1. **保存校验（P1，必做）**：`POST /api/settings/save` 时，校验 payload 中被置为 `true` 的 automation 键是否在该用户等级的 `features` 内，超权则 `400` 返回「该功能需要 VIP/SVIP」。这是防绕过的最小防线。
2. **前端呈现（P1，必做）**：设置页按等级渲染——超权开关直接隐藏或禁用并挂「VIP」角标，点击弹升级提示；账户中心展示权益对比表与等级到期时间。
3. **Worker 运行时校验（P2，可选）**：worker 执行任务前再查一次权益。防的是「降级前已保存的超权配置继续跑」；如果降级巡检做了 3.3 的开关重置，则这层可以不做。

单实例自售场景下，第 1 + 2 层已经足够；第 3 层属于纵深防御。

### 3.5 请求调度优先级（P2）

项目已有 `request-priority` / `low-priority-gate` 体系。映射方式：

```
账号 owner → 用户等级 → 账号请求基准优先级
svip: highest / vip: high / normal: normal（超管自身账号：highest）
```

改动点集中在 worker 的请求优先级取值处，读取账号配置时按归属用户等级换算。实现前需要先确认多用户并发下网关队列的实际竞争情况，避免过度设计。

| 侧栏 | 角色徽标升级为等级徽标（普通用户 / VIP / SVIP，超管仍显示超级管理员） |

## 五、分期实施建议

### P1 —— 最小可用（建议先做）

- 数据模型：用户 `level` / `levelExpiresAt`，卡密 `grantLevel`
- 卡密：生成时可选等级；注册/续费核销按 3.2 规则生效
- 门控：保存校验（3.4 第 1 层）+ 前端超权开关隐藏/禁用（第 2 层）
- 巡检：等级到期自动降级 + 超权开关重置
- 前端：账户中心权益展示、卡密/用户管理页的等级列与编辑
- 约涉及：`user-store`、`card-store`、`card-routes`、`auth-routes`（注册/续费）、`account-routes`（save 校验）、`admin/index.ts`（巡检）、`tier-permissions.ts`（新）、前端 5 个文件

### P2 —— 体验与公平性

- 请求调度优先级（3.5）
- 降级/升级时的账号日志与前端实时刷新（Socket 推送等级变更）
- 超管可调权益表（把 TIER_PERMISSIONS 搬进 store.json，面板可视化编辑）

### P3 —— 运营增强（可选）

- 更多卡种维度：单账号加时卡、功能体验卡（7 天 SVIP 试用）
- 用户侧消费记录（核销历史列表，现有卡密 `usedBy/usedAt` 已有数据，补一个查询页即可）
- 邀请返利等增长机制（依赖消费记录）

## 六、边界情况明细

| 场景 | 行为 |
| --- | --- |
| SVIP 用户购买普通时间卡 | 只延长账号有效期，等级不变 |
| VIP 用户购买 SVIP 卡 | 升级为 SVIP，等级时长叠加 |
| 等级到期但账号未到期 | 自动降级为普通，可正常登录，超权功能收回 |
| 账号到期但等级未到期 | 登录锁定（现状）；续费普通时间卡复活后，若等级仍在有效期则自动恢复权益 |
| 超管手动改等级 | 直接设置 `level` / `levelExpiresAt`，无需卡密 |
| 等级卡核销到超管实例（时间卡绑账号） | 与等级无关，忽略 `grantLevel` |
| 额度卡上限与等级上限 | 取 `max(等级基础上限, 额度卡叠加值)`，两者兼容 |
| 普通用户被降级时正在跑超权任务 | 降级巡检重置其账号 automation 开关，配置同步使 worker 停止对应任务 |
| 多张等级卡叠加 | `levelExpiresAt` 依次叠加，与现有时间叠加逻辑一致 |

## 七、运营与定价建议（供参考）

- **卡种组合**：普通时间卡（门槛）→ VIP 月卡 / 季卡 → SVIP 月卡 / 永久卡。永久 SVIP 定价要高于「10 年 SVIP」，避免长期负债感。
- **升卡引导**：VIP 用户购买 SVIP 卡时等级时长不重置而是叠加，鼓励直接升档。
- **试用**：发放 `grantLevel=svip` 的 7 天短时卡做体验，成本只是卡密生成的一条记录。
- **防滥用**：好友捣乱、神秘商人抢购留在 SVIP；这两类行为风控风险最高，付费墙也最高。
- **合规提醒**：本项目本身存在违反游戏服务条款的风险（见 README 免责声明），会员体系仅用于面板内部权益分发，不要对外宣传「游戏内特权」。

## 八、为什么不建议的其他方案

- **三套用户表**：注册/登录/隔离逻辑全部 ×3，维护成本远超一个 `level` 字段。
- **纯功能包（按功能单独卖卡）**：颗粒度太细，卡密类型爆炸，用户理解成本高；等级 + 额度卡叠加已覆盖绝大多数组合需求。
- **等级写进卡密核销记录反查**：核销历史做审计可以，但作为实时权益来源会让每次鉴权都要回放历史，性能与一致性都差。
